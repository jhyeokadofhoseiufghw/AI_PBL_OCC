## 📌 1. 시스템 아키텍처 및 화면 구조 (UI Architecture)

본 플랫폼의 모든 화면은 사방이 단단하게 결착된 사각형 격자 구조(Box Grid)를 준수하며, 사용자 목적에 따른 하이브리드 반응형(Hybrid Responsive) 규칙에 맞춰 분격 구현됩니다.

### 1) [관객용] 플랫폼 통합 홈페이지 (`/`) 
* **디자인 규격:** 반응형 크로스 플랫폼 (해상도별 가변 그리드 배치를 적용한 `Homely` 스타일 큐레이션 뷰)
* **도면 참조:** `1.txt`

### 2) [관객용] 공연 단독 피드 및 예매 랜딩페이지 (`/events/[eventSlug]`) 
* **디자인 규격:** 모바일 퍼스트 (max-w-md 중앙 정렬 래퍼 적용, 인앱 브라우저 최적화)
* **컴포넌트 룰:** 상단 좌측에 실제 공연 팜플렛 규격인 **세로형 A3 포스터 비율(1:1.414)**의 이미지 슬롯이 배치되며, 본문 상세 설명 영역과 하단 예매 정책 영역으로 구성됩니다. 기획자가 배포하기 전까지 빈칸 플레이스홀더 상태를 유지합니다.
* **도면 참조:** `2.txt`

### 3) [관객용] 실시간 좌석 선택 및 정보 입력 드로어 레이어 (`2-A 서브 컴포넌트`) 
* **디자인 규격:** 모바일 퍼스트 (하단 고정형 드로어 슬라이드 팝업 UI / Bottom Sheet)
* **실시간 동적 연산 로직:** 기획자가 입력한 고유 티켓 가격 상태값($P$)과 관객이 좌석 목록에서 선택한 좌석 수량($N$)을 실시간으로 바인딩하여 연산합니다 ($$\text{Total Price} = P \times N$$). 화면 이동 없이 한 공간에서 인적사항 입력 및 무통장 계좌 확인이 원스톱으로 이루어집니다.
* **비회원 보안 장치:** 회원가입 절차가 없는 대신, 추후 예매 조회를 위한 **4~6자리 정수형 '비회원 인증 비밀번호' 입력 필드**가 필수로 포함되며 입력 시 마스킹(`••••`) 처리됩니다.
* **도면 참조:** `3.txt`

### 4) [관객용] 비회원 예매 상태 조회 페이지 (`/reservation/status?event=[eventSlug]`, `/reservation/detail?event=[eventSlug]`) 
* **디자인 규격:** 모바일 퍼스트 (영수증 및 모바일 패스 스타일 UI)
* **상태별 컴포넌트 분기 인터랙션:**
    * **[⏳ 입금 대기]:** 기획자 입금 확인 전 단계. QR코드 영역이 안내 문구 격자로 대체됩니다.
    * **[✅ 예매 확정]:** 기획자 대시보드 승인 즉시 전환. 현장 입장을 위한 **고유 예매번호 및 고유 정적 QR코드**가 오픈됩니다.
* **도면 참조:** `4.txt` (대기중 상태), `5.txt` (완료 및 QR 오픈 상태)
* **조회 인증:** 특정 공연 컨텍스트 안에서 이름, 연락처, 조회 패스워드를 검증하며 티켓 ID만으로 개인정보나 QR을 공개하지 않습니다.

### 5) [기획자용 / Step 1] 공연 기본 정보 및 정책 입력 페이지 (`/dashboard/events/new`) 
* **디자인 규격:** 데스크톱 퍼스트 (보라색 고정 사이드바 `Slate-Purple` + 와이드 사각형 메인 패널)
* **입력 제어 및 컴포넌트 격리:** * `[Q2 메인 대표 포스터(A3)]` 등록 슬롯과 `[Q6 상세 설명 피드 이미지]` 등록 슬롯을 별도의 독립형 업로드 박스로 완전히 분리하여 데이터 오염을 방지합니다.
    * 티켓 가격 입력 칸과 1인당 최대 예매 매수 입력 칸은 불필요한 여백을 줄여 숫자가 들어갈 만큼 슬림하게 컴팩트 축소 마감했습니다.
* **도면 참조:** `9.txt`

### 6) [기획자용 / Step 2] 좌석 목록 생성 및 최종 배포 페이지 (`/dashboard/events/[id]/seats`) 
* **디자인 규격:** 데스크톱 퍼스트 (보라색 고정 사이드바 + 단순 좌석 목록 편집기)
* **인터랙션 파이프라인:** A1, A2 같은 좌석 라벨을 목록으로 추가·수정·비활성화합니다. 복잡한 행×열 맵 에디터와 통로 토글은 MVP에서 제외합니다.
* **`[👁️ 미리보기]` 엔드포인트:** 최종 배포 버튼 직전 트랙에 위치하며, 클릭 시 모바일 뷰포트 크기를 시뮬레이션하는 모달 레이어를 띄우고 브라우저 메모리의 임시 데이터를 주입하여 **2) 관객용 랜딩페이지 컴포넌트를 그대로 재사용(Reuse) 호출**합니다.
* **도면 참조:** `6.txt`

### 7) [기획자용] 엑셀 시트형 스마트 운영 관리 대시보드 페이지 (`/dashboard/events/[id]/reservations`) 
* **디자인 규격:** 데스크톱 퍼스트 (보라색 고정 사이드바 + 고밀도 엑셀 시트형 데이터 테이블)
* **다중 공연 운영 대응:** 대시보드 최상단에 **`[🎭 관리할 공연 선택 ▾]`** 드롭다운 컴포넌트 란이 탑재되어, 기획자가 여러 개의 공연을 등록하더라도 화면 리로드 없이 개별 공연의 통계 및 예매자 마스터 테이블 리스트로 즉각 전환(`Reactive Refetching`)할 수 있습니다.
* **도면 참조:** `7.txt`

### 8) [MVP 제외] 시스템 최고 관리자
* MVP의 권한 주체는 Organizer / Audience / System으로 한정합니다.
* 최고 관리자, 공연 강제내림, 전사 검색, 계정 발급, 장기 미입금 자동 취소는 제공하지 않습니다.
* **도면 참조:** `8.txt` (MVP 제외 정책 안내)

## 🔄 1-A. PRD 대조 보완 화면 및 상태

기존 ASCII 도면에 없지만 현재 PRD에 정의된 기능은 아래 화면/상태로 디자인 범위에 포함합니다. 상세 도면 제작 전까지 이 목록을 UI 계약으로 사용합니다.

### 관객 화면 보완
* **선착순 예매 상태:** 좌석 선택 없이 매수를 입력하고, 분류용 티켓 타입(일반/학생 등)이 설정된 경우에만 타입을 선택합니다. 나머지 비회원 정보와 계좌 확인 흐름은 `3.txt`를 재사용합니다.
* **단일 티켓 가격:** 선착순/좌석 지정 모두 공연별 단일 가격을 사용하며 `총액 = 공연 가격 × 예매 매수`로 표시합니다.
* **대기 신청:** 잔여 좌석 또는 수량이 없을 때 예매 CTA를 대기 신청 CTA로 전환하고 현재 상태가 `대기 신청`임을 티켓 상태 화면에 표시합니다.
* **직접 취소:** 공연별 취소 마감 전에는 예매 상세 화면에 취소 버튼과 마감 시각을 노출합니다. 취소 후에는 좌석/수량 복구 및 주최자 환불 문의 안내를 표시합니다.
* **체크인 완료 상태:** QR 스캔 완료 후 티켓 상태를 `입장 완료`로 표시하고 완료 시각을 노출합니다.
* **공연 상세 피드:** 공연 기본 설명 아래에 기획자가 작성한 이미지+본문 게시글 목록을 노출합니다.

### 기획자 화면 보완
* **인증:** `/signup`, `/login`에서 이메일, 비밀번호, 이름, 연락처, 단체명을 입력하며 인증 후 보호된 대시보드로 이동합니다.
* **공연 목록 및 상세 탭:** `/dashboard/events`와 공연별 개요, 좌석, 티켓 타입, 피드, 예매, 체크인 탭을 제공합니다.
* **피드 관리:** 공연별 이미지+본문 게시글 작성, 수정, 삭제 UI를 제공합니다.
* **대기열 관리:** 대기 신청 목록과 수동 예매 전환 액션을 예매 탭에 제공합니다.
* **QR 체크인:** `/dashboard/events/[id]/check-in`에서 후면 카메라 우선 스캐너, 권한/실패/재시도, 성공/중복 입장 결과와 체크인 로그를 제공합니다.
* **공연 상태:** 예정/진행 중/종료/비공개/취소 상태와 공개 URL 복사 기능을 개요 탭에 제공합니다.

### 디자인 파일 정합성 메모
* `6.txt`는 Step 2 단순 좌석 목록, `7.txt`는 기획자 예매 관리, `8.txt`는 최고 관리자 MVP 제외 안내입니다.
* `9.txt`는 Step 1 공연 기본 정보 입력 화면입니다.

## 🗄️ 2. [section-06-database-spec] 데이터베이스 모델 및 ERD 정의

DB 명세의 단일 진실 소스는 PRD `section-06-data-model.md`와 `db/schema.sql`입니다. Design 문서는 화면에 필요한 관계만 요약하며 별도 필드 체계를 만들지 않습니다.

### 1) 모델과 관계 요약
* **`organizers` → `events` (1:N):** 기획자는 여러 공연을 운영합니다.
* **`events` → `ticket_types` / `seats` / `reservations` / `feed_posts` (1:N):** 가격은 `events.ticket_price` 하나만 사용합니다.
* **`reservations` ↔ `seats` (N:M via `reservation_seats`):** 한 예매가 여러 좌석을 포함할 수 있고, 한 좌석은 동시에 하나의 활성 예매에만 연결됩니다.
* **선착순 잔여 수량:** `events.total_capacity - 활성 예매 quantity 합계`로 계산합니다.
* **좌석 지정 잔여 수량:** 활성 좌석 수에서 `reservation_seats`로 점유된 좌석 수를 차감합니다.

### 2) 가격과 상태 스냅샷
* 예매 생성 시 `events.ticket_price`를 `reservations.unit_price`에 복사하고 `total_price = unit_price × quantity`로 저장합니다.
* 이후 공연 가격이 바뀌어도 기존 예매 금액은 변경하지 않습니다.
* `reservation_code`와 `qr_token`은 입금 승인 후에만 생성합니다.
* 취소 시 선착순 수량을 복구하거나 `reservation_seats.released_at`을 기록해 좌석 점유를 해제하고, 선택 좌석과 예약 상태 이력은 보존합니다.

### 3) 조회 및 보안 인덱스
* 비회원 조회는 반드시 공연 식별자 + 이름 + 연락처 + 조회 패스워드를 함께 검증합니다.
* `reservations(event_id, reserver_phone)`, `reservations(event_id, status)`, 활성 `reservation_seats(seat_id)` partial unique 인덱스를 사용합니다.
